01Background

Why study binary trees? Because they are the most elegant tool for compression.

In a normal text file, every character uses a fixed number of bits. ASCII uses 8 bits per character, regardless of whether it is a space (very frequent) or the letter z (very rare). This is wasteful.

Huffman coding builds a binary tree to solve this problem: frequent characters sit closer to the root (short codes), while rare characters sit further down (long codes). Because no code is a prefix of another, this compression is completely lossless.

Example: For the text "ABRACADABRA":
  • Fixed 8-bit encoding: 11 chars × 8 = 88 bits.
  • Huffman encoding (A=0, B=10, R=110, C=1110, D=1111): 27 bits.
  • Compression ratio ≈ 30%, and decompression restores the original file perfectly.

02Project Requirements

Build a complete command-line compression tool.

2.1 Functional Requirements

IDRequirementAcceptance Criterion
F1 Read an input file Reads any ASCII file up to 1 MB correctly.
F2 Count byte frequencies Fills an int freq[256] array accurately.
F3 Build a Huffman tree Uses a min-heap to greedily merge the two smallest nodes. The root's frequency equals the file size.
F4 Generate prefix codes DFS from the root (left=0, right=1). No code is a prefix of another.
F5 Encode the file Writes a compressed file with a header and a bitstream.
F6 Decode the file Reconstructs the original file byte-for-byte identically.

2.2 Non-Functional Requirements

  • Written in C (C99), compiles with gcc -Wall -std=c99 with zero warnings.
  • No memory leaks — verified by valgrind.
  • Handles edge cases: empty file, single-character file, binary file with all 256 byte values.
  • The compressed file must be self-describing: the decoder can rebuild the tree using only the file header.
Design Decision: The decoder needs the frequency table to rebuild the tree. You must store the frequencies (e.g., 256 × 4 bytes) at the beginning of the compressed file. Do not forget to store the number of valid bits in the last byte so the decoder knows when to stop.

2.3 Command-Line Interface (Suggested)

./huffman compress   input.txt   output.huf
./huffman decompress output.huf  restored.txt

03Analysis Questions

Answer the following questions based on your implementation and tests.

  1. Tree construction: Why must we use a min-heap to build the Huffman tree? What would the time complexity be if we used a simple sorted array or an unsorted list instead?
  2. Prefix property: In your own words, explain why the Huffman tree guarantees that no code is a prefix of another. How does this property make decoding unambiguous?
  3. Edge cases: What happens if the input file contains only one unique character? How did you modify the tree construction to handle this case?
  4. Compression ratio: Which file type in your tests achieved the best compression ratio? Which achieved the worst? Explain why based on character frequency distributions.
  5. Memory management: Explain how you free the Huffman tree. Why is a postorder traversal the natural choice for freeing a binary tree?
